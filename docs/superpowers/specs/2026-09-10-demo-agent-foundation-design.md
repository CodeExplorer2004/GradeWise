# GradeWise 基础功能与 Agent 演示完善设计

## 背景

GradeWise 已具备四角色 RBAC、成绩数据、分析筛选、智能问数、图表、学情洞察、风险解释、批量报告、数据导入和 Docker 化运行能力。现阶段项目用于实习学习、现场演示和汇报，不以直接生产部署为目标。

当前主要不足是 Agent 任务元数据只保存在带 24 小时过期时间的 Redis 中，而实际线程和运行由内存版 Agent worker 保存。worker 重启后运行状态无法恢复，任务也可能从用户视角消失。现有 E2E 主要覆盖教务登录、问数和图表这一条正常路径，对多角色权限、导入和 Agent 故障路径覆盖不足。

## 目标与项目定位

本轮将项目定位为“production-aware demo”：基础业务真实可用，Agent 能力可解释、可演示，系统能够诚实处理内存 worker 的中断，但不模拟完整生产平台。

评审者应能明确看到：

1. 登录、角色权限、成绩范围、看板、导入和分析构成真实业务闭环。
2. Agent 使用经过服务端权限过滤和脱敏的数据，不能扩大数据范围或改变确定性统计结论。
3. Agent 任务有可查看的生命周期；worker 重启时任务记录仍在，并能标记中断和重新执行。

## 非目标

本轮不实现：

- 分布式任务的断点精确续跑。
- 生产级 Agent Server、高可用部署或完整服务间鉴权。
- 邮件、短信或企业消息通知。
- 大规模负载测试、故障注入和备份恢复演练。
- 完整刷新令牌撤销体系或生产 IAM。
- 大文件队列化导入和导入批次回滚。

以上内容保留为未来演进方向，不作为本轮完成条件。

## 方案选择

### 轻量演示型

只补充页面提示和演示用例，不改变任务存储。开发成本最低，但无法解决任务过期和 worker 重启后状态不明的问题。

### 平衡演示型（采用）

以 PostgreSQL 保存应用任务台账，保留内存 worker，增加中断识别、手动重试、真实阶段说明，并扩展核心业务和权限测试。该方案能清楚展示系统边界，改动规模适合实习项目。

### 准生产型

替换持久化 Agent Server，加入消息队列、完整认证、通知、监控和容灾。能力更完整，但会显著稀释项目的成绩分析与 Agent 主线，因此不采用。

## 用户演示闭环

```text
教务或教师登录
  -> 选择学年、年级、班级、考试或科目范围
  -> 查看权限范围内的成绩与学情概览
  -> 用自然语言提出分析问题
  -> 查看受限查询、统计结果、解释和图表
  -> 发起批量报告或预警任务
  -> 查看任务状态、结果或失败原因
  -> 对中断任务执行重试
```

智能问数与批量任务应明确区分。同步问数展示查询与图表闭环；批量任务展示独立 worker、任务生命周期和失败恢复边界。

## Agent 责任边界

确定性代码负责：

- 身份认证、角色授权和数据范围约束。
- 分析筛选校验、统计 SQL、参数化执行和 SQL 安全门。
- 风险分数、风险等级和确定性汇总。
- 学生标识脱敏、任务所有权和状态转换。

Agent 负责：

- 理解自然语言意图。
- 根据已授权证据组织解释和报告。
- 提出图表表达方式并生成受白名单约束的图表配置。
- 为确定性风险证据生成教学关注建议。

Agent 不得批准 SQL、扩大权限、重算风险等级、补造学生事实或将模型输出作为新的风险证据。

## Agent 任务数据模型

新增 PostgreSQL `agent_tasks` 表，作为应用任务的唯一事实来源。建议字段如下：

| 字段 | 用途 |
| --- | --- |
| `id` | 应用任务 UUID，独立于 worker thread ID |
| `school_id` | 学校隔离边界 |
| `user_id` | 任务所有者 |
| `task_type` | `batch_report` 或 `batch_warning` |
| `requested_scope` | 用户提交并规范化后的分析范围 JSON |
| `effective_scope` | 本次执行通过权限校验后的实际范围 JSON |
| `worker_thread_id` | 当前尝试对应的 worker 线程，可为空 |
| `worker_run_id` | 当前尝试对应的运行，可为空 |
| `status` | 应用任务状态 |
| `stage` | 当前可验证处理阶段 |
| `status_message` | 面向用户的简短状态说明 |
| `result` | 已脱敏的最终文本结果，可为空 |
| `error_code` | 稳定、可测试的错误码，可为空 |
| `attempt_count` | 已发起的执行次数 |
| 时间字段 | 创建、开始、完成和更新时间 |

任务表不长期保存完整学生证据。创建和重试时，根据任务类型、保存的 `requested_scope` 和当前用户权限重新计算 `effective_scope`、收集证据。这样可以减少敏感数据副本，并确保历史任务不能绕过当前权限。结果页面展示本次执行的 `effective_scope`，避免用户误解实际数据边界。

Redis 继续用于对话缓存，不再作为 Agent 任务列表和结果的事实来源。

## 状态机与故障语义

应用状态包括：

```text
queued -> running -> success
                  -> error
                  -> cancelled
                  -> interrupted
```

约束如下：

- 创建任务时先建立数据库记录，再提交 worker；提交成功后进入 `running`。
- 权限或范围校验必须在建立任务记录前完成；记录建立后的证据收集或提交失败应写入安全错误状态，使用户仍能看到并重试该任务。
- Worker 网络暂时不可用时返回服务不可用提示，但不立即把已有运行误判为中断。
- Worker 明确返回线程或运行不存在时，将非终态任务标记为 `interrupted`。
- `error` 和 `interrupted` 可以重试；其他状态拒绝非法重试。
- 重试保留应用任务 ID，重新校验权限、重新收集证据、创建新 worker 线程和运行，并增加 `attempt_count`。
- 重试状态转换必须在数据库事务中锁定任务行，防止重复点击产生多个并行运行。
- 取消成功后记录 `cancelled`；worker 暂不可达时不伪造已取消结果。
- 返回前端的错误信息必须经过归类，不暴露模型密钥、内部地址、堆栈或原始学生信息。

## 可观察阶段

页面只展示实际发生、可由系统验证的阶段：

```text
校验权限范围
  -> 收集并脱敏统计证据
  -> 提交 Agent
  -> Agent 生成报告
  -> 保存结果
```

内存 worker 当前只有一个模型节点，因此界面不得伪装详细“思维链”。同步问数可以展示范围已应用、SQL 安全校验、返回行数和图表类型等审计摘要，但不展示模型隐藏推理。

## API 与前端交互

保留现有任务创建、列表、详情、取消和追加要求接口。新增：

```http
POST /tasks/{task_id}/retry
```

所有任务接口都按当前登录用户和学校过滤。任务详情增加 `stage`、`status_message`、`attempt_count`、更新时间和可重试标记。

现有“追加要求”接口只在原 worker 线程仍存在时继续该上下文。如果一个已成功任务的 worker 上下文因重启消失，数据库中的成功结果保持不变，接口返回明确冲突提示，用户可创建新任务；不能把已经保存的成功结果改写为中断。

前端任务区域应提供：

- 清晰的状态标签和阶段说明。
- 创建范围、尝试次数和最近更新时间。
- 成功结果、失败原因或中断说明。
- 只在允许状态出现的“重新执行”操作。
- Agent 服务暂不可用时的非破坏性提示。

浏览器通知仍可作为便利功能，但页面内任务台账才是可靠的结果入口。

## 基础功能与测试矩阵

### Playwright 核心流程

隔离 Docker E2E 环境覆盖六类场景：

1. 网关公开存活与依赖就绪检查。
2. 教务登录、切换分析范围并看到对应看板数据。
3. 教务自然语言问数并得到答案、数据表和图表。
4. 学生只能查看本人数据，且不能创建批量 Agent 任务。
5. 任课教师只能分析获授权班级和科目。
6. 成绩文件导入显示接受行、拒绝行和明确错误原因。

权限场景同时验证页面能力和后端响应，不能只依赖隐藏按钮。

### Agent 任务专项测试

后端测试覆盖：

- 创建任务和数据库持久化。
- 用户与学校所有权隔离。
- Worker 成功结果持久化。
- 暂时连接失败不丢弃任务。
- Worker 线程不存在时转为 `interrupted`。
- 失败和中断任务的重试及尝试次数。
- 重试时重新执行角色和范围校验。
- 取消、非法状态转换和安全错误输出。

前端通过组件测试或接口模拟验证状态显示、失败提示和重试行为。自动化测试不调用外部大模型。

### 真实 Agent 冒烟演示

真实模型仅用于人工演示，准备三类稳定问题：

1. 最近一次考试各班成绩对比并生成图表。
2. 找出需要关注的学科或成绩变化，并解释已有证据。
3. 为指定权限范围生成批量学情报告。

模型未配置或不可用时，看板、确定性统计、权限控制和数据导入仍应工作。

## 低成本工程收尾

本轮可在核心闭环完成后补充以下低成本能力：

- 常见安全响应头和 Nginx 版本隐藏。
- 登录接口的基础限流。
- Python 依赖精确锁定和可复现漏洞审计记录。
- 更新架构说明、演示脚本和带日期的测试报告。

这些工作不得阻塞基础业务和 Agent 主线。

## 验收标准

本轮完成需要满足：

- Agent 任务数据库台账、故障识别和重试行为符合本设计。
- 四角色权限边界不因任务创建、查询或重试而被绕过。
- 后端测试、Ruff、Alembic 漂移检查、前端类型检查和生产构建通过。
- 隔离 Docker 环境中的核心 Playwright 场景通过。
- 真实 Agent 冒烟演示有可复用脚本；若模型服务不可用，测试报告必须明确记录，而不能声称通过。
- 架构文档清楚标注内存 worker、通知渠道和其他非生产边界。

## 建议实施顺序

1. Agent 任务模型、迁移和服务层状态机。
2. 任务 API、前端状态展示和手动重试。
3. Agent 任务专项测试和 worker 重启场景。
4. 多角色、看板、问数和导入 E2E。
5. 低成本安全与依赖收尾。
6. 演示脚本、架构说明和最终测试报告。
